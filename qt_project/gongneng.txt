【二】STM32 → 树莓派 当前串口数据协议
────────────────────────────────────────────────────────────────────────────────

```json
{
  "speed": 25.4,
  "cadence": 90,
  "power": 220,
  "slope": 3.5,
  "zt_flag": 5,
  "yaw": 60,
  "temperature": 26.5,
  "heart_rate": 145,
  "altitude": 60,
  "rear_dist": 12.5,
  "err_code": 0,
  "location": {
    "lat": 27.848011,
    "lon": 112.931726
  }
}
```

字段说明：
| 字段         | 类型  | 说明                                                    |
|--------------|-------|---------------------------------------------------------|
| speed        | float | 速度 km/h                                               |
| cadence      | float | 踏频 rpm                                                |
| power        | float | 功率 W                                                  |
| slope        | float | 坡度 %                                                  |
| zt_flag      | int   | 骑行状态：0=跌倒 1=右转弯 2=左转弯 3=上坡 4=下坡 5=正常 |
| yaw          | float | IMU 航偏角，0°指北，顺时针增加                          |
| temperature  | float | 温度 °C                                                 |
| heart_rate   | float | 心率 bpm                                                |
| rear_dist    | float | 后方来车距离 m                                          |
| err_code     | int   | 错误码（0=正常）                                        |
| location     | object| GPS 坐标 {lat, lon}                                     |

> 注：`distance`（骑行距离）和 `ride_time`（骑行时间）由树莓派端根据实时速度自行积分计算，STM32 无需发送。

【三】树莓派 ↔ App 通信协议与流程
────────────────────────────────────────────────────────────────────────────────

### 3.1 通信架构总览

树莓派作为服务端，同时维护三条独立通道，数据并行推送：

```
┌─────────────┐     18字节紧凑二进制      ┌─────────┐
│             │ ────────────────────────▶ │   App   │
│   树莓派    │     JSON (WebSocket)      │ (手机)  │
│  CommService│ ────────────────────────▶ │         │
│             │     JSON (MQTT)           │         │
│             │ ────────────────────────▶ │         │
└─────────────┘                           └─────────┘
```

- **BLE**：经典蓝牙 RFCOMM，走 `AppRealtimeData.to_ble_bytes()` 18字节紧凑格式
- **WiFi**：WebSocket (端口8765)，走完整 JSON，主力通道
- **MQTT**：broker.emqx.io，调试用，JSON 格式

### 3.2 实时数据（持续推送）

| # | 数据内容 | 触发条件 | 频率 | 通道 | 格式 | 缓存 |
|---|---------|---------|------|------|------|------|
| 1 | **传感器实时包**<br>速度、踏频、功率、距离、心率、坡度、温度、后方距离、GPS坐标、骑行状态 | `push_timer`<br>1Hz 定时器 | 1秒1次 | BLE+WiFi+MQTT<br>**并行推送** | BLE: 18B二进制<br>WiFi/MQTT: JSON | ✅ 始终进 BufferQueue<br>(30分钟/5000条上限) |
| 2 | **告警事件**<br>后方来车/心率过高/疲劳/跌倒/偏离路线 | AlertService<br>阈值触发 | 即时 | BLE+WiFi+MQTT<br>**并行推送** | JSON 事件 | ❌ 不缓存 |
| 3 | **骑行状态变化**<br>idle→riding→paused→finished | RideService<br>状态变化时 | 即时 | BLE+WiFi+MQTT<br>**并行推送** | JSON 事件 | ❌ 不缓存 |

**BLE 18字节紧凑格式** (`AppRealtimeData.to_ble_bytes()`)：
```
< 小端序 >
speed_x100      uint16   (km/h * 100)
cadence         uint16
power           uint16
distance_x100   uint32   (km * 100)
heart_rate      uint8
slope_x10       int8     (坡度 * 10)
temperature     int8
ride_state      uint8    (0=idle 1=riding 2=paused 3=finished)
timestamp       uint32
─────────────────────────────
总长度：18 字节
```

### 3.3 非实时数据（按需/低频）

| # | 数据内容 | 触发条件 | 通道 | 格式 | 说明 |
|---|---------|---------|------|------|------|
| 4 | **历史记录列表** | App 发送 `REQUEST_HISTORY` | WiFi+MQTT | JSON | 最近50条骑行摘要 |
| 5 | **FIT/GPX 文件** | App 发送 `REQUEST_FIT` / `REQUEST_GPX` | WiFi+MQTT | base64 JSON | 文件下载 |
| 6 | **断连缓存补发** | BLE/WiFi/MQTT 重连时 | 重连的通道 | JSON `buffer_sync` | 只补发该通道断开期间的数据 |
| 7 | **连接状态** | 客户端连接/断开 | PyQt 信号 | 回调 | 仅本地 UI+语音，不发给 App |

### 3.4 App → 树莓派 命令（下行）

App 通过 BLE / WiFi / MQTT **任一通道**发送 JSON 命令：

```json
{"cmd": "start_ride", "payload": {}, "timestamp": 1713980000}
```

| 命令 | 作用 | 处理位置 |
|------|------|---------|
| `START_RIDE` | 开始骑行 | main.py → RideService |
| `PAUSE_RIDE` | 暂停骑行 | main.py → RideService |
| `RESUME_RIDE` | 继续骑行 | main.py → RideService |
| `STOP_RIDE` | 结束骑行 | main.py → RideService |
| `SET_TARGET` | 设置功率/心率目标 | main.py |
| `LOAD_ROUTE` | 加载 GPX 路线 | main.py |
| `REQUEST_HISTORY` | 请求历史记录列表 | CommService 直接响应 |
| `REQUEST_FIT` | 请求下载 FIT 文件 | CommService 直接响应 |
| `REQUEST_GPX` | 请求下载 GPX 文件 | CommService 直接响应 |
| `UPDATE_CONFIG` | 更新用户配置 | main.py |
| `PING` | 心跳/连接检测 | 无操作 |

### 3.5 断连缓存补发机制

- **数据入口**：无论通道是否连接，每秒的传感器数据**始终**进入 `BufferQueue`
- **各通道独立维护 `last_push_time`**：BLE / WiFi / MQTT 分别记录最后成功推送的时间戳
- **重连触发补发**：某通道重连后，调用 `buffer_queue.get_since(last_push_time)` 取出断连期间的数据，按 50 条/批次补发
- **容量限制**：最多缓存 5000 条或 30 分钟，超出时滑动丢弃最旧数据

### 3.6 关键注意事项

1. **告警事件不缓存**：断连期间发生的告警会丢失，这是设计取舍（告警强调即时性）
2. **文件传输用 broadcast**：当前 FIT/GPX 回复通过 WiFi broadcast 发送，多客户端场景下所有连接者都会收到
3. **BLE JSON 兼容**：BLE 通道同时支持 18B 二进制（实时数据）和 `\r\n` 分隔的 JSON（事件/补发/欢迎消息）
4. **MQTT 公共 Broker**：使用 broker.emqx.io，Topic 建议后续增加设备唯一 ID 避免隐私泄露

【七】给 Claude Code 的开发提示
────────────────────────────────────────────────────────────────────────────────

1. 高德地图是在线的：当前 map_widget.py 依赖网络，户外无网会白屏。任何地图修改要考虑"离线可用性"。
2. 树莓派性能有限：Ollama 已通过 num_ctx=512、num_thread=4 优化。新增 heavy 计算要评估 CPU 占用。
3. DataContext 是中心数据源：所有需要向 LLM 提供上下文或向 UI 刷新的功能，都应通过 data_context.py 读写。
4. 语音模块已高度封装：drivers/audio/piper_voice.py 的 HybridVoicePlayer 支持离线/在线自动切换，优先复用。
5. BLE Server 在 Linux 上的坑：bleak 做 Server 资料比 Client 少，可能需要直接调用 bluez D-Bus API。
